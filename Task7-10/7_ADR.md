## **Название задачи:**
Онлайн-магазин «Мобильный мир» - Проектирование схем коллекций для шардирования данных

**Специфика MongoDB:**
- коллекция = таблица;
- документ = строка;
- на уровне бд реализована возможность шардинга по хешу, по диапазону;
- бд предоставляет набор атомарных операций чтение-апдейт;
- конкурентное обновление: запросы выстраиваются в очередь.

## **Решение**

### Описание существующей коллекции Products
```puml
entity Product {
    * product_id: number <<generated>>
    --
    * name: text
    * category: text
    * price: number
    * geo_leftovers: array
    attributes: json
}
```
**Профиль нагрузки:**
- коллекция содержит ограниченное количество документов;
- очень частые чтения по категории, цене;
- сам каталог товаров обновляется значительно реже, чем читается;
- массив остатков продукта обновляется очень часто, "конкурентными" процессами.

| **Решение**                                                                           | **Техническая реализация** | **Обоснование**                                                                                                                                                                                                                                                                      |
|---------------------------------------------------------------------------------------|------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1. Отделить динамическую информацию об остатках от статической информации о продукте. | Вертикальное партиционирование по geo_leftovers | В существующей коллекции Products совмещены статические и динамические, часто изменяющиеся, данные продуктов. Это выглядит неэффективным с точки зрения возможности кэширования не часто изменяющейся информации о продукте. В текущем виде коллекцию сложно эффективно шардировать. |
|                                                                                       |                                    |
 Итак, предлагается разделить коллекцию на две, каждая из которых может быть эффективно масштабирована горизонтально:
```puml
entity Product {
    * product_id: number <<generated>>
    --
    * name: text
    * category: text
    * price: number
    attributes: json
}
```
**Коллекция Products**
- содержит редко изменяющиеся данные, следовательно, их можно эффективно закешировать (Redis/CDN/...);
- при большом объеме продукции к коллекции Products можно применить шардирование по категории товара (чтобы сохранить эффективный поиск по категории):
```javascript
sh.shardCollection(
    "db.Products", 
    {category: "hashed"}
)
```
```puml
entity ProductLeftover {
    * product_id: number <<generated>>
    --
    * geo: text
    * quantity: number
    * updated_at: timestamp
}
```
**Коллекция ProductLeftovers**
- содержит часто изменяющиеся данные;
- может быть шардирована по product_id - что даст равномерное распределение данных.
- может быть шардирована по гео-зоне - что даст изоляцию нагрузки по регионам:
```javascript
sh.shardCollection(
    "db.ProductLeftovers", 
    {geo: 1, product_id: 1}
)
```
Пример атомарного списания остатков:
```javascript
db.ProductLeftovers.findOneAndUpdate(
  { product_id: X, geo: "Moscow", quantity: { $gte: qty } },
  { $inc: { quantity: -qty } }
)
```

#### **Недостатки, ограничения, риски**
1. Разделение коллекций потребует дополнительные правки кода, а также миграцию исторических данных, что может привести к увеличению сроков модернизации, а также к потере\порче критических данных об остатках.
2. Шардирование коллекции Products по категории товара может привести к неравномерному распределению данных, если кол-во товаров в категориях сильно отличается.
3. Шардирование коллекции ProductLeftovers по гео-зоне может привести к неравномерному распределению данных, если одна гео-зона сильно отличаются по кол-ву покупателей\интенсивности покупок.

### Описание существующей коллекции Orders
```puml
entity Order {
    * order_id: number <<generated>>
    --
    * user_id: number
    * created_at: timestamp
    * products: array
    * status: text
    * total_sum: number
    * geo: text
}
```
**Профиль нагрузки:**
- коллекция содержит исторические данные и актуальные заказы авторизованного пользователя;
- заказы создаются постоянно => объем данных постоянно растет;
- исторические заказы, преимущественно, читаются (история по пользователю)

| **Решение**                                                           | **Техническая реализация**            | **Обоснование**                                                                                                                                                                   |
|-----------------------------------------------------------------------|---------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1. Обеспечить локальность заказов одного пользователя.                | Шардирование по user_id + created_at. | Хешированное шардирование даст равномерное распределение данных. Все заказы одного пользователя окажутся на одном шарде => поиск истории пользователя будет происходить локально. |
| 2. Как альтернатива - обеспечить локальность заказов внутри гео-зоны. | Шардирование по geo + created_at.     | Тут нужно смотреть на бизнес-логику процессинга заказов.                                                                                                                          |
|                                                                       |                                       |

Пример шардинга по пользователю:
```javascript
sh.shardCollection(
    "db.Orders", 
    {user_id: "hashed", created_at: 1}
)
...
find({user_id: X}).sort({created_at: -1})
```
Пример шардинга по гео:
```javascript
sh.shardCollection(
    "db.Orders", 
    {geo: 1, created_at: 1}
)
```

### Описание существующей коллекции Carts
```puml
entity Cart {
    * cart_id: number <<generated>>
    --
    user_id: number
    session_id: number
    * items: array
    * status: text
    * created_at: timestamp
    * expires_at: timestamp
    updated_at: timestamp
}
```

**Профиль нагрузки:**
- корзина относится либо к авторизованному пользователю, либо к посетителю;
- возможна миграция корзины от посетителя к авторизованному пользователю;
- одна корзина содержит ограниченное кол-во товаров;
- корзины создаются постоянно, но так же постоянно трансформируются в заказы\удаляются по ttl => объем таблицы не растет на долгой дистанции;
- частое обновление статуса и списка товаров.


| **Решение**                                                         | **Техническая реализация**       | **Обоснование**                                                                                                                                                                  | Недостатки                                                                                                                                                               |
|---------------------------------------------------------------------|----------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1. Ничего не менять.                                                |                                  | Если логика подразумевает хард-делит старых корзин по ttl, то на долгой дистанции объем коллекции не растет. Соответственно для поиска достаточно индексирования данных.         | На распродажах может быть всплеск создания и операций над корзинами. Надо анализировать реальную нагрузку. Тут нужно смотреть на бизнес-логику процессинга заказов.      |
| 2. Как альтернатива - распределение по пользователю.                | Шардирование по user_id + status. | Если мы примем решение шардировать заказы по user_id, то неплохо бы шардировать и корзины по тому же пользователю. Это обеспечит локальность при формировании заказа из корзины. | Корзина может принадлежать неавторизованному посетителю => такие корзины будут располагаться на одной шард-ноде, что опять же грозит всплеском нагрузки при распродажах. |
| 3. Как альтернатива - распределение по суррогатному идентификатору. | Шардирование по owner_id + status. | Корзина может относиться как к авторизованному пользователю, так и к неавторизованному посетителю.                                                                               | Усложняем систему; дополнительная разработка.                                                                                                                            |
| 4. Как альтернатива - добавить в коллекцию данные о гео.            | Шардирование по geo + status. | Гео-зону авторизованного пользователя мы знаем. У посетителя мы можем попросить предварительно выбрать зону доставки, либо определить по ip.                                     | Возможно неравномерное распределение данных.                                                                                                                             |
